# 小林面试笔记 RAG 问答系统

把 [小林面试笔记](https://xiaolinnote.com) 的知识库做成一个可以自己提问学习的检索增强问答系统。知识库现在覆盖两个站点、235 篇笔记：小林面试笔记（AI 应用开发方向，122 篇）与[小林coding](https://www.xiaolincoding.com)（计算机基础方向，113 篇）。

不是调 LangChain 拼一个 demo，而是把 RAG 的每个环节自己实现一遍：**父子切割、Contextual Retrieval、多 Query 展开、向量 + BM25 多路召回、RRF 融合、重排精排、质量门控、引用溯源**，再加上**按内容寻址的增量构建**。每个模块都能单独讲清楚原理和取舍。

## 效果

在自建评测集上（58 道有目标页的题目，覆盖两个站点 10 个栏目，另加 4 道库外样本做拒答断言）：

| 层 | 指标 | 结果 | 参考线 |
|----|------|------|--------|
| 检索层 | Hit@5（精排后） | 0.983 | ≥ 0.8 |
| 检索层 | MRR（精排后） | 0.848 | ≥ 0.5 |
| 检索层 | 8 道冷门探测题（高频域低出现字段） | 8/8 排第 1 | — |
| 检索层 | 4 道库外样本 | 4/4 被门控拒答（最高分 0.072 < 0.3） | — |

58 题里唯一未命中的 `hard-03` 是「目标文章在融合 top-5 之外」的难例；本轮多 Query 展开正是治「复合问题被主导话题挤占」这类失败（见下）。**生成层裁判分本轮未跑**（生成层判分口径的改动经用户裁定暂缓，见下）。

门控阈值仍取 0.3，未重新校准。06 轮评测换成了**全库口径**（不再按栏目预过滤，跨栏目混淆进入统计），并加进 8 道冷门探测与 4 道库外断言样本。已知边界：重排器度量内容重叠，库外问题若恰好撞上库内重头戏（实测「React 调度器」对库内大片「调度」内容打到了 0.4~0.8），门控可能放行——此时由生成层诚实兜底（答「知识库中未找到」不编造），详见 `docs/06-多Query扩展.md`。

> 这些数字来自 2026-09-20 的一次实测。换模型会变：用 `deepseek-v4-flash` 构建的那版索引，融合后 Hit@5 是 0.967，换成 `deepseek-v4.1-flash` 后是 1.000。裁判分数也存在轮次波动（历史上出现过 4.90），单次分数不宜当作恒定值。
>
> 另外，上游向量服务对同一段文本**并非逐位确定**（实测同一 query 连测三次，最大绝对差 0.0016、余弦 0.9999）。所以两次独立运行的向量分数、融合顺序、重排分数，以及生成模型最终选择引用哪几条，都会略有不同——这不是本地链路的不稳定。

## 架构

```
离线构建（xiaolinrag build）
  markdown 笔记 → 父子切分 → Contextual Retrieval 背景生成 → 子块向量化
                                    ↑                              ↓
                          上一版索引按内容复用            FAISS 向量索引 + entries.jsonl + BM25 语料

在线问答（xiaolinrag serve；浏览器打开 http://127.0.0.1:7860）
  问题 → 多 Query 展开（LLM 拆角度，原 query 恒在首位）
       → 每个 query 各跑 向量 top20 + BM25 top20 ─┴→ RRF 融合 → 聚焦精排（max 聚合）
                                                      ↓ 通过门控
                                        取 top5 子块映射父块 → 生成 → 答案 + 引用
  答案与引用原文 → markdown 渲染（表格/列表/链接/图片）
  引用原文里的图片 → GET /kb/<文章所在目录>/assets/… → 从 kb/ 读图（受限）
```

**五个关键设计**

1. **父子切割**：子块（约 300 字）用于向量检索定位，父块（约 900 字）用于喂给模型阅读。小块检索准、大块上下文全，代价是存储翻倍。
2. **Contextual Retrieval**：入库前让模型看着全文给每个子块写一句背景说明，与原文拼接后再向量化，缓解孤立子块「没头没尾」导致的召回偏差。按文章成批生成（一篇文章一次调用），把 7000+ 次调用压到 300 次量级。
3. **多 Query 展开**：检索前让模型把用户问题拆成多个角度的检索 query（原 query 恒在首位），每个 query 独立召回后 RRF 融合；精排改用各聚焦 query 打分、按块取 max 聚合——复合 query 不再整体打分，广告块在聚焦视角下自然降权。治「三次握手+四次挥手」这类多子话题问题被主导话题挤占。
4. **质量门控**：重排最高分低于阈值就直接拒答，不让生成模型在低质量上下文上硬编。库外样本以 `expect_rejected` 标记进评测集，评估断言门控确实挡下它们。
5. **增量构建**：背景生成与向量化都按内容寻址——文章的正文没变就直接沿用上一版索引里的背景说明与向量，只对新增/改动的内容发起调用。**索引产物仍是整体重建**（三行行号照样对齐），省掉的只是对外部服务的调用。

实测增量效果（235 篇 / 7053 子块）：

| 场景 | 背景说明 | 向量 | 耗时 |
|------|---------|------|------|
| 首次全量（旧索引与当前模型对不上） | 重生成 235 篇 | 新算 7053 条 | 46 分钟 |
| 内容未变，重建 | 命中 235 篇 | 命中 7053 条 | **4.4 秒** |
| 只改一篇文章的正文 | 命中 234 篇 | 命中 7035 条，新算 18 条 | 21 秒 |

## 快速开始

```bash
# 1. 环境（独立 conda 环境）
conda create -n xiaolinrag python=3.11 -y
conda activate xiaolinrag
pip install -e ".[dev]"

# 2. 准备知识库：把爬取产物整份拷进项目根的 kb/（markdown 与 assets/ 都要）
#    体积约 1.9 GB，已在 .gitignore 中，不进版本控制
cp -a /path/to/xiaolin-kb ./kb

# 3. 配置
cp config.example.yaml config.yaml   # 按需改 kb_dir / index_dir / 模型名
cp .env.example .env                 # 填入两个 API Key
#   SILICONFLOW_API_KEY   —— 向量化与重排（https://api.siliconflow.cn）
#   CHAT_API_KEY          —— 对话生成与评估裁判（OpenCode Go 网关）

# 4. 构建索引（首次约 45 分钟：235 次背景生成 + 7053 条向量化，视服务端速度浮动）
python -m xiaolinrag build
python -m xiaolinrag status          # 查看索引规模与检索参数

# 5. 启动问答界面（接口与前端由同一进程提供）
python -m xiaolinrag serve           # 浏览器打开 http://127.0.0.1:17860

# 6. 离线评估（可选）
python -m xiaolinrag eval            # 检索层 Hit@5/MRR + 生成层 LLM 裁判
python -m xiaolinrag eval --no-judge # 只跑检索层
```

**首次构建很慢，之后很快**：只有第一次要为全部内容付费。之后再跑 `build`，内容没变的文章会命中复用，几秒就能跑完；只有新增或改动过的文章才重新生成。构建日志会打印命中/未命中的数量。

换了知识库内容才需要重建索引；只改 `kb_dir` 的指向不必重建——索引里存的都是文本与标识，不含文件系统路径。

`.env` 与 `config.yaml` 都已在 `.gitignore` 中，密钥不会进入版本控制；`status` 与报错信息里的密钥一律打码。

默认使用的模型（都在 `config.yaml` 里，随时可换）：

| 环节 | 模型 | 提供方 |
|------|------|--------|
| 子块向量化 | `Qwen/Qwen3-Embedding-8B`（4096 维） | 硅基流动 |
| 候选精排 | `BAAI/bge-reranker-v2-m3` | 硅基流动 |
| 答案生成 | `deepseek-v4.1-flash` | OpenCode Go 网关 |
| Contextual Retrieval 背景生成 | `deepseek-v4.1-flash` | OpenCode Go 网关 |
| 评估裁判 | `deepseek-v4.1-flash` | OpenCode Go 网关 |

换对话模型后需要重建索引——背景说明是构建时由对话模型生成的。索引里记录了生成它的模型名（`status` 可见），模型一变，复用会整批关闭，背景说明全部重新生成，不会把旧模型写的东西当成新模型的结果。

网关要求的额外请求头写在 `config.yaml` 的 `models.chat_extra_headers` 里（当前网关需要 `x-opencode-session`，是客户端自行生成的会话标识，不参与鉴权）。换成不需要该头的网关时整段删掉即可。

## 实现要点

**切分**（`chunking.py`）：markdown 解析成语义块，按标题层级分组，组内按段落打包成子块；代码块、表格、列表整块保留不截断；段落自身超限时按句子边界回退。

**检索**：向量通道用 FAISS `IndexFlatIP` + 归一化向量（等价余弦相似度），栏目过滤走 `IDSelectorBatch`；关键词通道用 jieba 分词 + `BM25Okapi`。每条 query 各自两路取 top20，「多 query × 双通道」统一交给 RRF（k=60）按排名融合——回避了向量相似度和 BM25 分数不可比的问题。**多 Query 展开**在检索前把复合问题拆成多个角度的 query（原 query 恒在首位），RRF 泛化融合后，精排由 `rerank_aggregate` 用各聚焦 query 打分、按块取 max 聚合——复合 query 不参与打分，避免分数注水（详见 `docs/06-多Query扩展.md`）。

**两级检索范围**：栏目键是「站点/栏目」复合键（如 `xiaolincoding/network`），保证两个站点将来出现同名栏目也不会串。按站点筛选就是传该站点的全部栏目键，接口契约不变。

**三路行号对齐**：FAISS 行号 = `entries.jsonl` 行号 = BM25 文档序，由 build 一次性建立，load 时校验，不一致直接提示重建。

**增量复用**（`reuse.py`）：上一版索引里已经存着每个子块的原文、背景说明与向量，所以只要键按内容算，复用就自然成立，不需要另立一份缓存文件。背景说明的键是「文章的子块序列 + 切分参数」，向量的键是「送入向量化的文本」；模型名不进键，改为在索引元信息里记录并由复用源显式比对——否则同一个模型换个 ID 写法就会把全部文章误判成「变了」。读不到、读坏了都退化成全量，不阻断构建。

**引用溯源**：提示词里资料带 `[n]` 编号，模型在答案里标 `[n]`，系统按编号映射回文章标题、栏目、原文链接和父块原文；越界编号（悬空引用）会记入 debug 供核查。

**界面**（`static/`）：独立前端，原生 HTML/CSS/JS，不引入构建工具、包管理器或外链资源。筛选按站点分组，站点级复选框可一键全选该站点的栏目。答案按 markdown 子集渲染（**先整体转义再套标记**，原文里的 HTML 不会被执行），支持标题、列表（含嵌套）、表格、围栏代码块、引用块、粗体、斜体、删除线、行内代码、链接与图片；答案中的 `[n]` 是锚点，点击直接跳到对应引用卡片。

**引用原文**与答案共用同一条渲染链路，所以卡片里的粗体、表格、图片都会正常呈现。语料里的图片引用（`assets/<文章>/<文件>`）以**文章所在目录**为基准拼成 `/kb` 地址——站点的目录层级不固定，按文章定位一条规则就覆盖所有深度。`/kb` 只允许读取知识库 `assets/` 目录下的 png/jpg/jpeg/gif/webp，越界路径、非图片扩展名、不存在的文件一律 404，且响应不透露服务器目录。站内相对链接（`/ai/rag/1.html`）以引用的出处地址为基准补成完整 URL，可以点开看原文。

**门控拒答**以独立样式的提示框呈现，与正常答案明确区分。

## 已知边界

- 知识库共 3252 张图片，其中 **1 张 svg 不提供**（svg 可内嵌脚本，按白名单设计一律 404），前端降级为可读文本、原图链接照旧可点
- 只覆盖 markdown 笔记，官方 PDF（`original_xiaolin`）留给后续模块
- 笔记正文里的图片会在引用卡片中显示，但**图片不参与检索**——不做多模态向量化，也仍只支持文字提问
- 图片不做缩放或裁剪，原图直出，展示尺寸由样式约束
- 不做 HyDE / Step-back Prompting、不做多轮对话（多 Query 展开已做；其余改写方法留给后续模块）
- 界面不做流式输出，答案一次性返回；不做移动端原生适配，窄屏可用但未专门优化
- `kb/` 是知识库的一次性副本，与原库**不自动同步**；原库更新后需重新拷贝
- 评测集为自建，题目表述偏规范，指标偏乐观；真实提问的措辞多样性未被充分覆盖
- **复用源就是上一版索引**：把 `data/index/` 删掉再构建就是全量（46 分钟），这与「缓存丢了」是同一件事，不是故障
- 构建跑到一半中断（如向量化阶段报错）会丢掉本次已生成的成果，下次需重来——这是「不另立缓存文件」这个取舍的已知代价
- 门控阈值 0.3 没有随评测集更换重新校准
