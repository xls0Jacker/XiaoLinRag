# 模块解读 05：多站点知识库与增量复用

> 本文拆解知识库换代这一轮改动：`xiaolinrag/corpus.py`、`xiaolinrag/reuse.py`，以及
> 随之调整的索引元信息、提示词、接口与前端图片地址。讲清「两个站点、变深目录」怎么接进来，
> 以及「重建时不为没变过的内容重复付费」是怎么做到的。
> 全文基于本项目 `xiaolinrag/` 包（模块解读，供自研参考）。

## 1. 模块职责

本轮之前，知识库只有一个站点、目录形状固定为「栏目/文章」；爬虫换代后变成两个站点、
目录变成「站点/栏目/[章节]/文章」，索引文件也从顶层栏目清单改成按站点分组。同时构建
一直是彻底的全量重建——103 篇时能接受，235 篇且还会继续长的时候就不划算了。

| 文件 | 本轮职责 |
|------|---------|
| `corpus.py` | 按新索引格式发现语料；文章带站点、栏目用「站点/栏目」复合键；递归容纳章节子目录 |
| `reuse.py` | 新增。把上一版索引当复用源，按内容寻址取回背景说明与向量 |
| `contextual.py` | 背景生成接复用源，命中即跳过调用 |
| `index_store.py` | 索引元信息记录对话模型、站点与栏目展示名；`IndexEntry.site` 做成派生属性 |
| `prompts.py` | 展示名改由外部传入；系统提示词覆盖「AI 应用开发 + 计算机基础」两类内容 |
| `pipeline.py` / `api.py` | 透传展示名；引用带上文章标识；图片路径形状放宽到任意深度 |
| `cli.py` | 构建时接复用源、只对未命中项向量化、打印命中统计；`status` 显示站点 |
| `static/` | 筛选按站点分组；引用图片地址改以文章所在目录为基准 |

边界：只负责「把新语料读进来」与「少花重复的钱」，不碰切分、融合、重排、门控、生成的算法。

## 2. 核心数据结构

### `Page`（`xiaolinrag/corpus.py`）

```python
@dataclass
class Page:
    page_id: str   # 相对知识库根去扩展名，如 "xiaolincoding/network/1_base/tcp_ip_model"
    site: str      # "xiaolincoding"
    section: str   # 复合键 "xiaolincoding/network"
    title: str
    source_url: str
    text: str
```

`page_id` 就是文章的相对路径。它一路派生出 `chunk_id` / `parent_id`（`page_id#c0`），
所以子块与父块的标识自动变成全域唯一，切分器一行没改。

### `SiteInfo` / `SectionInfo`（`xiaolinrag/corpus.py`）

```python
@dataclass
class SectionInfo:
    key: str        # 复合键
    site: str
    label: str      # 展示名，如 "图解网络"——取自索引文件，不是代码常量
    page_count: int

@dataclass
class SiteInfo:
    key: str
    label: str      # "小林coding"
    sections: list[SectionInfo]
```

### `ReuseSource`（`xiaolinrag/reuse.py`）

```python
class ReuseSource:
    @classmethod
    def load(cls, index_dir, cfg) -> "ReuseSource"   # 读不到就是空源，绝不抛异常
    available -> bool          # 上一版索引读进来了没有
    reason -> str              # 人话说明（「对话模型已从 X 变为 Y，背景说明需重新生成」）
    context_key(child_texts, cfg) -> str
    contexts(key) -> list[str] | None
    vector_key(embed_text) -> str
    vector(key) -> np.ndarray | None
    stats -> ReuseStats
```

## 3. 关键流程

### 构建链（含复用判定）

```
load_pages / load_sites         → Page[]（带 site、复合 section）、SiteInfo[]
ReuseSource.load(index_dir)     → 复用源（读不到就是空源）
split_page(每篇)                 → ChildChunk[] / ParentChunk[]
enrich(children, pages, cfg, reuse=reuse)
   每篇先算「文章子块序列 + 切分参数」的键
   命中 → 按序写回背景说明，不发调用
   未命中 → 走原有分批调用
组装 IndexEntry[]（含复合 section）
向量化：
   命中 → 直接取复用源里的向量
   未命中 → embed_documents(仅未命中项)
   按原行序拼成完整矩阵
build_meta(含 chat_model / 站点与栏目展示名)
IndexStore.build + save         → 三件套整体重写
```

**关键点：索引产物仍是整体重建。** `entries.jsonl` 与 `index.faiss` 全量重写、三路行号
照样对齐；复用省掉的只是对外部服务的调用。

### 查询链（只多一次标签透传）

```
api.read_answer
 → pipeline.ask(question, cfg, store, sections=[复合栏目键…])
     store.search_vector / search_bm25（按复合键过滤）
     fuse_rrf → rerank → 门控
     prompts.build_user_prompt(..., labels=store.meta["section_labels"])
     parse_citations(..., labels) → Citation（含 page_id）
 → api.CitationOut → 前端
```

按站点筛选不需要后端新参数：**传该站点的全部栏目键即可**，接口契约一字未改。

### 引用图片地址

```
corpus 里的引用：assets/<文章>/<文件>   ← 相对「文章所在目录」
文章标识：xiaolincoding/os/1_hardware/how_cpu_run
基准 = 标识去掉最后一段 → /kb/xiaolincoding/os/1_hardware/assets/how_cpu_run/08.png
```

## 4. 要点小结

1. **栏目为什么用「站点/栏目」复合键，而不是直接用栏目名？**
   两个站点各自有一套栏目体系。现在恰好没有重名，但把站点编进键里，将来任何一边新增
   一个叫 `network` 的栏目都不会串到一起。代价只是键长一点。

2. **为什么复用源直接用上一版索引，不另立一份缓存文件？**
   上一版索引里本来就存着每个子块的原文、背景说明与向量，行号还是对齐的。键只要按内容
   算，复用就自然成立。少一套文件格式，也就少一类「缓存与索引版本对不上」的故障；「缓存
   文件没了」天然等价于「上一版索引没了」，退化成全量而已。已知代价：构建跑到一半中断
   （比如向量化阶段报错）会丢掉本次已生成的成果，下次得重来。

3. **模型名为什么不塞进哈希键，而是写进元信息再显式比对？**
   最初的设计是把模型名放进键里。实际踩到了：同一个模型换个 ID 写法（网关从
   `deepseek/deepseek-v4.1-flash` 改成 `deepseek-v4.1-flash`），键就全变了，整整 102 篇
   没动过的文章被判定成「全变了」。改成把 `chat_model` / `embedding_model` 写进索引元
   信息、由复用源显式比对，语义清楚得多；顺带补上一个缺口——原先元信息根本不记录背景
   说明是哪个对话模型生成的，README 里写着「换对话模型后建议重建」却无从判断。

4. **`site` 为什么不落库，做成由 `page_id` 首段派生的属性？**
   文章标识的首段恒为站点，存一份就是允许两份数据互相打架。更实际的理由是：不加字段，
   **旧版的条目文件仍然读得进来**——否则换了 schema 之后，对着旧索引跑 `status` 会看到
   一句英文的 `TypeError`，而不是「索引是旧版本，请重新构建」。

5. **图片基准为什么取「文章所在目录」，而不是按站点固定切几刀？**
   目录层级本身就不固定：小林面试笔记是「站点/栏目/文章」，小林coding 还要多一层章节。
   实测全部 3265 条图片引用都是统一的 `assets/<文章>/<文件>` 形状，所以「以文章目录为基
   准」一条规则就覆盖了所有深度，不必按站点写特例。

6. **为什么仍然不提供 svg？**
   全库只有 1 张 svg。svg 可以内嵌脚本，作为 `<img>` 加载虽不执行也没有纳入的理由。前端
   对加载失败本来就有降级路径（渲染成可读文本、原图链接照旧可点），所以这一张的代价是
   可见的、且不影响其余 3252 张。

### 附：10 个栏目的展示名

出处行（提示词里的 `《标题》（栏目 · 标题路径）`）只写栏目展示名，不叠站点名——实测这
10 个名字两两不重复，再叠一层是冗余：

| 站点 | 栏目展示名 |
|------|-----------|
| 小林coding | 图解网络 / 图解系统 / 图解MySQL / 图解Redis |
| 小林面试笔记 | RAG / 工具调用 / LLM / LangChain / Agent / 图解Claude Code |

## 5. 测试绑定

**对应的测试文件：**
- `tests/test_corpus.py` —— 新索引格式解析、递归发现章节子目录、与索引集合对账、展示名顺序
- `tests/test_reuse.py` —— 复用源的命中/未命中/自失效/降级/顺序无关
- `tests/test_contextual.py` —— 命中时不调用模型、条数不符时重算、无复用源时行为不变
- `tests/test_index_store.py` —— 索引元信息与站点点属性
- `tests/test_pipeline.py` —— 展示名透传与兜底、引用带文章标识
- `tests/test_api.py` —— 元信息按站点分组、嵌套深度的图片端点、路径安全
- `tests/test_frontend_js.py` —— 引用图片地址在两种深度下都拼对

**怎么验证本模块：**
- 整文件（全绿）：`python -m pytest tests/test_reuse.py tests/test_corpus.py -q`
- 单条用例：`python -m pytest tests/test_reuse.py::test_chat_model_change_disables_context_reuse -q`
- 端到端（消耗额度）：`python -m xiaolinrag build` 观察两行「背景复用 / 复用命中」统计

**需要知道：**
- `docs/testing.md` 是全部测试的入口与总表，可反查任意模块。
- 本模块无存量失败，新增用例全部使用替身，不发起真实模型调用。
- mock 测不到的部分：真实语料的篇数与块数、构建日志里的命中/未命中数量、界面上的分组排版
  与图片是否真的加载出来——这些靠一次真实构建 + 界面走查验证，结论记在当轮 `checklist.md`。
- 语料相关数字（篇数、子块数、父块数、评测指标）来自某次实测，语料或模型变化后需重跑
  `python -m xiaolinrag eval` 复核，不要当成恒定断言。
