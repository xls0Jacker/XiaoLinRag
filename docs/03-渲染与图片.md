# 模块解读 03：渲染扩展与知识库内置

> 本文拆解 `xiaolinrag/static/app.js` 的 markdown 渲染器、`xiaolinrag/api.py` 的图片端点，
> 以及项目内置的知识库副本 `kb/`。
> 全文基于本项目 `xiaolinrag/` 包（模块解读，供自研参考）。

## 1. 模块职责

模块 02 的渲染能力是有意收窄的：markdown 只支持标题、列表、代码块、引用块与基本行内标记，引用原文按纯文本展示。真用起来立刻暴露三处：

- 模型返回的答案里有表格，渲染后整张表塌成一段带竖线的文字
- 引用原文里的 `**Chroma**`、`![](...)` 以源码形式出现在卡片里
- 笔记正文的 672 处配图既没有渲染逻辑，也没有提供它们的途径

模块 03 把渲染补齐，并给图片开一条受限的读取通道。

| 文件 | 职责 |
|------|------|
| `static/app.js` | markdown 渲染器（表格、嵌套列表、链接、删除线、图片）；引用原文接入渲染；图片加载失败降级 |
| `static/styles.css` | 折叠改为高度钳制 + 遮罩；表格、图片、卡片内小标题样式 |
| `api.py` | `GET /kb/{path}` 图片端点与 `_resolve_asset` 的四道检查 |
| `kb/` | 知识库副本（两个站点、235 篇 markdown + 3252 张图片），`kb_dir` 指向它。模块 05 换了新一代产物，见 `docs/05-多站点知识库.md` |

**边界**：本模块不动任何业务逻辑。`pipeline.py` / `chunking.py` / `retrieval.py` / `reranker.py` / `index_store.py` / `corpus.py` / `config.py` 全部零改动——尤其是**索引不需要重建**，理由见要点小结第 6 条。

## 2. 核心数据结构

### 渲染选项（`static/app.js`）

```javascript
renderMarkdown(markdown, options = {})
// options.resolveImage: (src)  => string | null   能加载的地址，或 null 表示降级
// options.resolveLink:  (href) => string | null   能打开的地址，或 null 表示只留文字
```

渲染器**不知道**自己身处哪个知识库、哪篇文章。它只调用调用方给的解析器，拿不到地址就降级。于是「知识库目录怎么布局」只出现在调用处一处：

```javascript
// buildCitationCard 里
excerpt.innerHTML = renderMarkdown(citation.excerpt, {
  resolveImage: (src) => (src.startsWith("assets/") ? `/kb/${citation.section}/${src}` : null),
  resolveLink: (href) => { /* 以 citation.source_url 为基准补成完整 URL */ },
});
```

答案正文不传解析器——模型生成的图片引用无从判断属于哪篇文章，一律降级为文本。

### 行内交替正则（`static/app.js`）

```javascript
const INLINE = new RegExp([
  "`([^`]+)`",                                        // 1 行内代码
  "!\\[([^\\]]*)\\]\\(([^)]+)\\)",                    // 2,3 图片
  "\\[([^\\]]+)\\]\\(((?:[^()\\s]|\\([^()]*\\))+)\\)", // 4,5 链接
  "\\*\\*([^*]+)\\*\\*",                              // 6 粗体
  "~~([^~]+)~~",                                      // 7 删除线
  "\\*([^\\s*][^*]*?)\\*",                            // 8 斜体
  "\\[(\\d{1,3})\\]",                                 // 9 引用编号
].join("|"), "g");
```

**这个数组的顺序就是优先级**，两条最容易踩：

1. 图片与链接必须排在引用编号之前——否则 `[1](url)` 会先被编号分支吃掉，渲染成 `[1]` 加一段文本
2. `**` 与 `~~` 必须排在 `*` 之前——否则粗体与删除线会被斜体分支切碎

链接地址那一支写成 `((?:[^()\s]|\([^()]*\))+)` 而不是 `([^)]+)`，是为了容忍一层括号。写成 `[^)]+` 时 `javascript:alert(1)` 只会吃到第一个 `)`，剩下的 `)` 留在正文里——模块 02 因为「原样回显」这个 bug 被掩盖了，模块 03 输出纯文字才暴露出来。

### 图片路径契约（`api.py`）

```
GET /kb/<文章所在目录>/assets/<文章>/<文件>
```

```python
IMAGE_TYPES = {
    ".png": "image/png", ".jpg": "image/jpeg", ".jpeg": "image/jpeg",
    ".gif": "image/gif", ".webp": "image/webp",
}
ASSET_SEGMENT = "/assets/"   # 形状检查：路径里必须出现这一层，且不以 / 开头
```

media type 显式写死而不是靠 `mimetypes` 猜：标准库**不认识 `.webp`**（返回 `None`），而语料里正好有 135 张 webp。白名单不收 svg——svg 可以内嵌脚本，即使作为 `<img>` 不执行也没有纳入的理由（当前语料里有 1 张，前端降级为可读文本）。

路径形状为什么不写死层级：模块 05 接入第二个站点后，目录变成「站点/栏目/[章节]/文章」，层级数不固定（`xiaolinnote/rag/4_chunking` 是两层，`xiaolincoding/os/1_hardware/how_cpu_run` 是三层）。形状检查只要求「路径里有 `assets/` 这一层」，真正的越界拦截交给第 ③ 步的 `resolve` 后判界。

## 3. 关键流程

### 3.1 块级解析（`renderMarkdown`）

```
escapeHtml(markdown)          ← 第一步就把 < > & " ' 全部实体化
  ↓ split 成行
  ↓ 逐行判定（顺序即优先级）：
      围栏 ```           → 整块原样，不处理行内标记
      空行                → 冲刷当前块
      标题 #{1,4}         → h(级数+1)，一级标题留给页面
      表格                → 需「本行以 | 起止」且「下一行是分隔行」
      列表 -/*/+ 或 1.    → 记下缩进，交给 renderList 建栈
      引用块 >            → 注意此时已是 &gt;
      其余                → 累积成段落
  ↓ 各块调 renderInline()
  ↓ join 成 HTML
```

表格那一步的两个条件缺一不可：只看竖线会把正文里偶尔出现的 `|` 误判成表格；只看「下一行有横线」会把 `---|---` 之外的东西也吸进来。

### 3.2 引用卡片的渲染与图片请求

```
buildCitationCard(citation)
  ↓ resolveImage = (src) => citationImageUrl(citation.page_id, src)   # 以文章所在目录为基准
  ↓ excerpt.innerHTML = renderMarkdown(citation.excerpt, { resolveImage, resolveLink })
  ↓ 浏览器遇到 <img src="/kb/xiaolincoding/os/1_hardware/assets/how_cpu_run/08.png">
GET /kb/xiaolincoding/os/1_hardware/assets/how_cpu_run/08.png
  ↓ _resolve_asset 四道检查：
      ① 形状   不以 / 开头，且路径里出现 assets/
      ② 扩展名 必须在 IMAGE_TYPES 白名单内
      ③ 判界   root.resolve() → (root/raw).resolve() → is_relative_to(root)
      ④ 存在   必须是文件
  ↓ FileResponse(media_type=…)
  ↓ 加载失败 → 容器上捕获阶段的 error 监听把 <img> 换成可读文本
```

`error` 事件**不冒泡**，所以监听必须挂在容器上并传 `capture: true`；也正因如此，没有在 `<img>` 上写内联 `onerror`。

### 3.3 折叠：从行数到高度

模块 02 用 `-webkit-line-clamp: 6`，它要求内容是**行内元素**——遇到 `<table>`、`<ul>`、`<img>` 这类块级子元素会直接失效。模块 03 换成：

```css
.excerpt.clamped {
  max-height: 15rem;
  overflow: hidden;
  mask-image: linear-gradient(to bottom, #000 65%, transparent);
}
```

底部用 `mask-image` 做渐隐，表示「下面还有」。这是**功能性遮罩**，不是装饰性背景渐变——模块 02 的 checklist 里有一条「`grep gradient` 为 0」，本模块据此把该条改成「不含装饰性背景渐变，`mask-image` 遮罩允许」，而不是把阈值悄悄调松。

## 4. 要点小结

1. **为什么表格识别要两个条件，而不只看竖线？**
   正文里 `|` 是个普通字符（代码、正则、`或` 的简写都可能出现）。要求「本行以 `|` 起止」且「下一行是分隔行」之后，误判概率降到可忽略——而且这两个条件都是 markdown 表格本身必须有的结构，不是额外发明的启发式。代价是必须带上外层竖线的表格才认（模型输出的表格都带）。

2. **为什么行内标记用单次交替正则，而不是「挖出代码、处理完再放回去」的占位符方案？**
   单次 `replace` 从左到右扫描并消费匹配，**已替换出来的标签不会被再次扫描**，天然避免了「粗体里再套粗体」的互相污染，也不需要哨兵字符。占位符方案有个隐蔽代价：哨兵如果用不可见字符（比如 NUL），它会以真实字节的形式留在源码里，编辑器里完全看不出来——模块 02 就踩过这个坑。代价是**顺序变得极其重要**，所以正则分支旁边必须写明为什么这么排。

3. **图片端点为什么必须先 `resolve()` 再判界，不能先判字符串？**
   字符串层面看 `rag/assets/../../../etc/passwd.png` 仍然以 `rag/assets/` 开头，形状检查完全放行。`resolve()` 会展开 `..` 与符号链接，展开之后再用 `is_relative_to(root)` 判界，才真正拦住。测试里专门放了一个指向 `/etc/passwd` 的符号链接——只有「解析后判界」这个顺序能挡住它。

4. **四类失败（形状不符、扩展名不符、越界、不存在）为什么返回同一句话、同一个状态码？**
   区分「路径非法」与「文件不存在」等于向探测者确认「这个目录是存在的，只是文件名不对」——一次探测就能把目录结构试出来。统一成 404 `资源不存在`，失败之间不可区分，探测拿不到任何增量信息。响应体里也不带服务器绝对路径，测试里对这一点单独断言。

5. **为什么渲染器接受 `resolveImage` 回调，而不是自己知道知识库的布局？**
   渲染器一旦知道 `/kb/<文章所在目录>/assets/…` 这个规则，它就和「知识库目录怎么组织」绑死了，也没法在 node 里独立测试。改成回调之后，渲染器只知道「有一个 src，问调用方能不能加载」，知识库布局只出现在引用卡片那一处；路径规则变了只改一个地方（模块 05 把基准从「栏目」换成「文章目录」时，渲染器与它的测试确实一行没动，只换了 `citationImageUrl` 的实现）。

6. **为什么换了 `kb_dir` 却不用重建索引？**
   索引里存的 `IndexEntry` 全是文本与标识：`chunk_id` / `page_id` / `section` / `title` / `source_url` / `heading_path` / `child_text` / `context_note` / `parent_text` / `seq`——**没有任何文件系统路径**。所以只要知识库内容本身没变，把 `kb_dir` 从项目外指到项目内，索引依然有效。这一条在验收时是实测的：改完配置直接 `status`，显示「已就绪」，没有跑过 `build`。省下的不只是几分钟，还有一次全量构建的 API 消耗。

7. **为什么知识库是拷贝而不是引用原目录？**
   原目录是爬虫项目的输出，项目想跑起来就得依赖它存在。拷贝进 `kb/` 之后项目在磁盘上自包含；代价是多了一份会静默变旧的副本，所以 `kb/` 明确不进版本控制、也不做自动同步——原库更新后重新拷贝即可。1.9 GB 里绝大部分是图片，这是它不能进 git 的唯一原因。

## 5. 测试绑定

**对应的测试文件：**

- `tests/test_api.py` —— 图片端点的六类拒绝路径、四类穿越形态（含 URL 编码与符号链接）、webp 的显式 media type、失败响应不泄漏服务器路径
- `tests/test_frontend_js.py` —— 表格（结构/对齐/单元格内标记/负例）、链接（协议白名单、相对路径补全、与引用编号互不误伤）、删除线、嵌套列表、图片（有解析器出 `img` / 无解析器降级）

**怎么验证本模块：**

- 整文件（全绿）：`python -m pytest tests/test_api.py -q -k asset`
- 整文件（全绿）：`python -m pytest tests/test_frontend_js.py -q`
- 单条用例：`python -m pytest tests/test_api.py::test_resolve_asset_rejects_directly -q`
- 单条用例：`python -m pytest tests/test_frontend_js.py::test_table_renders_structure -q`

**需要知道：**

- `docs/testing.md` 是全部测试的入口与总表，可反查任意模块。
- 本模块**无存量失败**。
- `test_frontend_js.py` 需要 `node`，未安装时整份跳过；跳过不等于通过。
- mock 测不到、需要真实链路的部分：图片是否真的显示出来、大图加载是否可接受、折叠遮罩的实际观感、窄屏下表格是否破版。这些靠真实服务 + headless 截图逐项走查，结论记在当轮 checklist。
- 语料里的图片共 672 处引用、671 个文件（544 PNG + 127 WebP）。这个数字来自某次实测，语料更新后需重新核对。
